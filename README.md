# Cosmo Tech extra configs
*Optional Configuration Settings for Cosmo Tech Platforms*

## Requirements
* Working Kubernetes cluster (AKS) deployed from Cosmo Tech terraform-azure (for **stacks/postgres**)
* Working Kubernetes tenant deployed from Cosmo Tech terraform-tenant (for **stacks/keycloak**)
* [![Terraform](https://img.shields.io/badge/Terraform-7B42BC?style=flat-square&logo=terraform&logoColor=white)](https://developer.hashicorp.com/terraform/tutorials/aws-get-started/install-cli)
## Project structure
This project is organized in **independent stacks**, one per module, each with its own
Terraform state. This means you can `plan`/`apply` a single stack (e.g. `postgres`) without
any risk of impacting another stack's resources (e.g. `keycloak`), and vice-versa.

```
terraform-extra/
  _run-terraform.sh           # entry point script, run against a specific stack
  modules/                    # reusable Terraform modules
    azure_postgres_flexible/
    azure_postgres_autostartstop/
    config_keycloak_idp/
  targets/                    # backend templates per cloud_provider (shared across stacks)
  stacks/                     # one folder per independent, deployable stack
    postgres/                 # root module for azure_postgres_flexible (own state)
    keycloak/                 # root module for config_keycloak_idp (own state)
```

## How to
* Clone & open the repository
    ```
    git clone https://github.com/Cosmo-Tech/terraform-extra.git --branch <tag>
    cd terraform-extra
    ```
* Deploy
    * Pick the stack you want to work on: `postgres` or `keycloak`
    * Fill `stacks/<stack>/terraform.tfvars` variables according to your needs
    * Run pre-configured script, giving the stack name as first argument
        * Plan
            > Get an execution plan to preview the changes without applying
            * Linux
                ```
                ./_run-terraform.sh <stack>
                ```
                for example:
                ```
                ./_run-terraform.sh postgres
                ./_run-terraform.sh keycloak
                ```
            * Windows
                ```
                ./_run-terraform.ps1 <stack>
                ```
        * Apply
            > executes the operations proposed in the plan
            * Linux
                ```
                ./_run-terraform.sh <stack> --apply
                ```
                for example:
                ```
                ./_run-terraform.sh postgres --apply
                ./_run-terraform.sh keycloak --apply
                ```
            * Windows
                ```
                ./_run-terraform.ps1 <stack> --apply
                ```

## Developpers
* modules
    * **terraform-extra**
        * *config_keycloak_idp* = add an Identity Provider on the top of an existing Keycloak (for exemple set Okta as IdP for Keycloak). Deployed via the `keycloak` stack (`stacks/keycloak`).
        * *azure_postgres_flexible* = deploy an Azure Database for PostgreSQL Flexible Server (naming `csm-<resource_group_name>`), configure firewall rules (AKS Load Balancer IP(s), always discovered automatically; Cosmo office; Cosmo datacenter). Admin credentials are auto-generated by Terraform (`random` provider) and never printed in clear (`sensitive = true`). Database provisioning is handled by another Terraform config. Deployed via the `postgres` stack (`stacks/postgres`, Azure only).
        * *azure_postgres_autostartstop* = optional feature (disabled by default) that deploys an Azure Function App (Python, timer-triggered) to automatically start/stop the PostgreSQL Flexible Server on a schedule (UTC, Monday to Friday, public holidays skipped), to save costs outside business hours. Works with a server created by `azure_postgres_flexible` in this stack, or with an already-deployed server referenced read-only (see `postgres_server_already_exists`). Deployed via the `postgres` stack (`stacks/postgres`, Azure only).
* Terraform **stacks & state**
    * Each stack under `stacks/` has its **own, independent Terraform state**, isolated per (stack). This guarantees that running `plan`/`apply` on one stack (e.g. `postgres`) never proposes changes or destruction of resources belonging to another stack (e.g. `keycloak`).
    * States are stored beside the cluster Terraform state, in the current cloud s3/blob storage service (generally called `cosmotech-states` or `csmstates<id>`, depending on what the cloud provider allows in naming convention). The state key/blob name includes the stack name, e.g. `tfstate-<cluster>-<postgres>` (no tenant needed) vs `tfstate-<cluster>-tenant-<tenant>-keycloak`.
* Terraform **outputs & credentials**
    * After a successful `--apply`, `_run-terraform.sh`/`.ps1` automatically reminds you how to reveal sensitive outputs (e.g. PostgreSQL admin credentials), without needing to `cd` into the stack folder yourself:
        ```
        terraform -chdir=stacks/<stack> output -raw <output_name>
        ```
    * Sensitive outputs (`administrator_login`, `administrator_password`, ...) stay marked `sensitive = true` on purpose: this hides them from `plan`/`apply`/`output` logs (terminal history, CI logs, screen shares), while still letting you fetch the raw value on demand with `-raw` to copy/paste into Vault.
